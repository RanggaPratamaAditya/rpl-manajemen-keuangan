## 4.3 Tinjauan Kode dan Keamanan

Peninjauan kode (*code review*) dan audit keamanan dilakukan secara terstruktur sebelum pengemasan rilis `v1.0.0` dengan mengacu pada daftar periksa keamanan web OWASP Top 10:2025 serta kebutuhan nonfungsional keamanan pada spesifikasi proyek. Pemeriksaan difokuskan pada empat aspek krusial, yakni pengendalian akses antarperan (`KF-07`), validasi masukan pengguna (`KF-03`), perlindungan kueri basis data terhadap injeksi (`KF-05`), serta pengelolaan rahasia dan konfigurasi lingkungan produksi. Setiap temuan dicatat pada berkas `docs/laporan-temuan.md`, diperbaiki pada branch kerja terpisah, lalu diverifikasi kembali melalui pengujian otomatis dan uji regresi cepat sebelum digabungkan ke branch `main`.

| ID Temuan | Lokasi Berkas | Deskripsi Temuan & Risiko | Kategori OWASP 2025 | Status & Bukti Perbaikan |
|---|---|---|---|---|
| `T-01` | `templates/transaksi_list.html` | Tombol **Hapus** sempat ditampilkan pada antarmuka peran `kasir`; meski rute server menolak dengan `403`, tampilan tombol membingungkan pengguna. | `A01:2025` Broken Access Control | Diperbaiki (pembatasan kondisional Jinja2 peran `pemilik`, teruji di `tests/test_rilis.py`) |
| `T-02` | `percobaan.py`, `app.py` | Belum ada pembatasan percobaan masuk berulang sehingga akun berisiko terhadap serangan tebak sandi otomatis (*brute-force*). | `A07:2025` Authentication Failures | Diperbaiki (kunci sementara 5 menit setelah 5 gagal masuk, teruji di `tests/uji_cepat.py`) |
| `T-03` | `models.py` | Karakter *wildcard* SQLite (`%` dan `_`) pada kata kunci pencarian transaksi berpotensi memicu pencocokan berlebih bila tidak di-escape. | `A03:2025` Injection | Diperbaiki (kueri berparameter disertai *escape* karakter khusus pada fungsi pencarian) |
| `T-04` | `app.py`, `.gitignore` | Potensi penggunaan `SECRET_KEY` bawaan yang lemah pada lingkungan produksi serta risiko ter-commit-nya berkas basis data lokal. | `A05:2025` Security Misconfiguration | Diperbaiki (penolakan start produksi tanpa `SECRET_KEY` kuat & isolasi `*.db` di `.gitignore`) |

*Sumber data: `docs/laporan-temuan.md`, `percobaan.py`, `app.py`, dan log keluaran `tests/uji_cepat.py`.*

Hasil tinjauan menunjukkan bahwa kerentanan logika kontrol akses dan kesalahan konfigurasi tidak selalu menimbulkan pesan galat ketika aplikasi dijalankan pada alur normal. Pada temuan `T-01`, rute penghapusan transaksi pada `app.py` sebenarnya sudah dilindungi dekorator `@wajib_pemilik`, tetapi ketidaksinkronan pada lapisan presentasi menyebabkan tombol aksi tetap terlihat oleh staf kasir. Perbaikan dilakukan dengan menyelaraskan kondisi tampilan pada `templates/transaksi_list.html` serta memastikan seluruh formulir `POST` menyertakan token CSRF secara konsisten.

```html
<!-- Sebelum perbaikan (tombol muncul untuk semua peran) -->
<form method="post" action="{{ url_for('hapus_transaksi', transaksi_id=item['id']) }}">
    <button type="submit">Hapus</button>
</form>

<!-- Sesudah perbaikan (hanya dirender untuk peran pemilik + token CSRF) -->
{% if g.pengguna['peran'] == 'pemilik' %}
<form method="post" action="{{ url_for('hapus_transaksi', transaksi_id=item['id']) }}">
    <input type="hidden" name="csrf_token" value="{{ csrf_token() }}">
    <button type="submit">Hapus</button>
</form>
{% endif %}
```

Pelajaran utama dari tahapan tinjauan kode dan keamanan ini adalah bahwa mekanisme perlindungan harus diterapkan secara berlapis (*defense in depth*) pada sisi server sekaligus dicerminkan secara konsisten pada antarmuka pengguna. Selain itu, penerapan pemeriksaan otomatis pada `app.py` yang menolak menjalankan aplikasi ketika `APP_ENV=production` tanpa variabel `SECRET_KEY` yang valid terbukti efektif mencegah kelalaian manusia saat pemasangan produksi, dan pengujian otomatis terhadap celah pelanggaran akses jauh lebih andal dibandingkan pemeriksaan manual semata.
